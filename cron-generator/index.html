    About Cron Expressions

    Cron expressions are the standard way to define scheduled tasks on Unix-like operating systems and in many job-scheduling frameworks. A standard cron expression consists of five fields—minute, hour, day of month, month, and day of week—separated by spaces. Each field can contain a single value, a range (e.g., 1-5), a list (e.g., 0,15,30), a step (e.g., */5), or an asterisk (*) meaning "every."     Understanding Cron Syntax: The Five Fields Explained

    A standard cron expression consists of five fields separated by spaces: minute hour day-of-month month day-of-week. Each field accepts specific value types that determine when a task runs. The minute field (0–59) controls which minute of the hour the job executes. The hour field (0–23) selects the hour in 24-hour format. The day-of-month field (1–31) specifies the calendar day. The month field (1–12 or JAN–DEC) restricts execution to specific months. The day-of-week field (0–7, where both 0 and 7 represent Sunday, or SUN–SAT) targets particular weekdays.

    Each field can use several operators to create flexible schedules. An asterisk (*) means "every possible value" for that field. A hyphen (-) defines a range, like 9-17 for hours 9 AM to 5 PM. A comma (,) creates a list of specific values, like 0,15,30,45 for every 15 minutes. A slash (/) defines a step interval, where */5 means "every 5 units" and 10-50/10 means "every 10 units starting from 10 through 50."

    Some implementations also support special shortcuts. For example, @daily is equivalent to 0 0 * * *, @hourly equals 0 * * * *, @weekly equals 0 0 * * 0, and @reboot runs once at system startup. Quartz Scheduler and Spring Framework add an optional sixth field for seconds, and a seventh optional field for years, giving even finer control over scheduling.

    Cron Expression Examples Table

    Here are commonly used cron expressions with their plain-English descriptions. These cover most scheduling needs you'll encounter:

    • * * * * * — Every minute (useful for development and testing)
    • */5 * * * * — Every 5 minutes (health checks, polling)
    • */15 * * * * — Every 15 minutes (log rotation, metrics collection)
    • */30 * * * * — Every 30 minutes (cache refresh, data sync)
    • 0 * * * * — Every hour at minute 0 (hourly reports)
    • 0 */2 * * * — Every 2 hours (batch processing)
    • 0 */6 * * * — Every 6 hours (database backups)
    • 0 0 * * * — Every day at midnight (daily reports, cleanup)
    • 0 2 * * * — Every day at 2:00 AM (off-peak maintenance)
    • 0 9 * * * — Every day at 9:00 AM (morning digest emails)
    • 0 9 * * 1-5 — Weekdays at 9:00 AM (business-day tasks)
    • 0 0 * * 0 — Every Sunday at midnight (weekly maintenance)
    • 0 0 * * 1 — Every Monday at midnight (weekly reports)
    • 0 0 1 * * — First day of every month at midnight (invoices, billing)
    • 0 0 1 1 * — January 1st at midnight (yearly tasks, license renewals)
    • 0 0,12 * * * — Twice daily at midnight and noon
    • 30 8 1,15 * * — At 8:30 AM on the 1st and 15th of each month (payroll)
    • 0 18 * * 5 — Every Friday at 6:00 PM (end-of-week summaries)

    Cron Timezone Considerations

    One of the most common sources of cron-related bugs is timezone confusion. Traditional Unix cron runs in the server's local timezone, which means a cron job set for 0 9 * * * (9:00 AM) executes at 9:00 AM in whatever timezone the server is configured for. This becomes problematic when servers are deployed across multiple regions, when daylight saving time transitions occur, or when the server timezone differs from the business timezone.

    Modern scheduling systems handle this differently. AWS EventBridge allows specifying a timezone in the rule definition. Kubernetes CronJobs use the timezone of the Kubernetes control plane. Spring's @Scheduled annotation can use a configured ZoneId. If precise timezone control is critical for your application, always verify the execution timezone explicitly rather than assuming the server default.

    Daylight saving time presents a unique challenge for cron. When clocks spring forward, the hour between 2:00 AM and 3:00 AM is skipped, which can cause jobs scheduled during that hour to be missed entirely. When clocks fall back, that hour repeats, potentially causing jobs to execute twice. For critical tasks, consider using UTC (which has no DST transitions) or scheduling around the 2:00–3:00 AM window during DST transition periods.

    Cron Use Cases and Real-World Applications

    Cron jobs are the backbone of automated task scheduling across the software industry. Here are the most common use cases where cron expressions are essential:

    System maintenance: Automate log rotation, temporary file cleanup, disk space monitoring, database vacuum operations, and system health checks. These tasks typically run during off-peak hours to minimize impact on active users.

    Data backups: Schedule regular database dumps, file system snapshots, and incremental backups to remote storage. Common patterns include hourly incremental backups, daily full backups, and weekly/monthly archive rotations.

    CI/CD pipelines: Trigger nightly integration test suites, scheduled deployments, container image rebuilds, and dependency vulnerability scans. Many CI/CD platforms including GitHub Actions, GitLab CI, and Jenkins support cron-based pipeline triggers.

    Cloud infrastructure: Schedule auto-scaling actions, start/stop development environments during off-hours to save costs, rotate SSL certificates, and synchronize resources across availability zones. AWS, Azure, and GCP all support cron-based scheduling natively.

    Email and notifications: Send daily digest emails, weekly newsletters, monthly billing statements, scheduled reminders, and expiration warnings. These often combine cron scheduling with template rendering and email delivery services.

    Frequently Asked Questions

    What is a cron job?

    A cron job is a scheduled task that runs automatically at specified intervals using cron, a time-based job scheduler built into Unix-like operating systems. Cron jobs are defined by cron expressions (five fields: minute, hour, day, month, weekday) and are managed by the cron daemon, which continuously checks for and executes scheduled tasks. Modern alternatives include systemd timers, AWS EventBridge, Kubernetes CronJobs, and cloud-based schedulers.

    How does cron work?

    The cron daemon runs as a background process and wakes up every minute to check the crontab (cron table) for any jobs scheduled to run at that exact minute. If the current time matches the cron expression's five fields (minute, hour, day of month, month, day of week), the corresponding command is executed. Each user typically has their own crontab, and system-wide cron jobs are stored in /etc/crontab or /etc/cron.d/.

    What are the most common cron schedules?

    The most common schedules include every minute (* * * * *), every 5 minutes (*/5 * * * *), hourly (0 * * * *), daily at midnight (0 0 * * *), weekdays at 9 AM (0 9 * * 1-5), weekly (0 0 * * 0), and monthly (0 0 1 * *). See the examples table above for a comprehensive list with descriptions.

    What timezone does cron use?

    Traditional Unix cron uses the server's local system timezone. This means you need to know the server's timezone setting when creating schedules. For applications with users in multiple timezones, consider using UTC or specifying the timezone explicitly in modern scheduling systems. Always verify the timezone to avoid scheduling surprises, especially around daylight saving time transitions.

    What happens when day-of-month and day-of-week are both specified?

    In standard cron, when both day-of-month and day-of-week are restricted (not asterisks), the job runs when either condition is met, not both. For example, 0 0 13 * 5 runs at midnight on the 13th of each month AND on every Friday, not only when the 13th falls on a Friday. This is OR logic, which differs from the intuitive AND expectation. Some implementations like Quartz Scheduler use AND logic instead.

This helps verify your schedule is correct before deploying to production. The parser supports standard five-field cron syntax and runs entirely in your browser.
