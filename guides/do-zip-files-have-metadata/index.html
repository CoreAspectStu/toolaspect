Do ZIP Files Have Metadata?

📄 6 min readUpdated November 11, 2026

Yes. A ZIP archive records more than the files you put in it: folder paths, modified times, and with some tools a numeric user ID, file permissions and the time each file was last opened. A password doesn't hide the file names, either. We built archives with three tools, read the bytes, and tested five ways to clean them up.

What metadata does a ZIP file store?

A ZIP keeps a small record for every file and folder inside it, and anyone can read those records without unpacking a thing. We built the same test folder (a text note, a .docx and a photo) with three tools on a Debian 12 machine: Info-ZIP zip 3.0, Python 3.11.2's zipfile module and 7-Zip 26.02. Then we read the raw bytes and checked our parser against zipinfo -v.

Python wrote the least. zip wrote the most: its extra fields cost 52 bytes per entry, and they're on by default.

Can a ZIP file show your username or folder names?

Yes, if you zip by full path. We ran zip -r out.zip /home/jsmith/Documents/tax-2025 from a test account, and every entry name began with home/jsmith/. zip dropped the leading slash and kept the rest. Change into the folder first and names start where you want them to.

The user ID is a number. We found no account name in any extra field.

How exact are the timestamps, and do they show your time zone?

The basic time field holds even seconds only, in local time. Our note was last saved at 09:26:53 UTC. zip and 7-Zip stored 20:26:54, the Sydney clock time rounded up. Python stored 20:26:52.

With the clock set to New York, then Tokyo, the same file got 05:26:54 and 18:26:54. The field follows the zipper's clock.

Default zip output gives away more, because it stores local time and UTC side by side: 20:26:54 and 09:26:53. Subtract, and you know the sender's clock ran 11 hours ahead of UTC. The same record held the moment each file was last opened.

Does a password hide the file names in a ZIP?

No. A ZIP password scrambles each file's contents and leaves the list of files readable. We locked the test folder three ways and tried to list each archive without the password.

7-Zip .7z with -mhe=onNoIt wouldn't open without the password

unzip -l printed every name, size and date from the first two, and extracting failed, as it should. If the names are the secret, a .zip won't keep it.

What do Mac and Windows add?

We couldn't make these ourselves, so we read public samples: a test file from the libarchive project and several from the Go source tree, each labeled with the tool that made it.

The libarchive Mac sample held one 8-byte file plus two extras, a __MACOSX/ folder and a 287-byte ._file3 inside it. That hidden twin carried the file's access list, with account names in readable text. All three Mac samples stored user ID 501 and a last-opened time.

The Windows 7 and Windows XP samples held names, local times and basic file attributes. The WinRAR, WinZip and 7-Zip ones added modified, accessed and created times at sub-second precision.

We didn't measure Windows 11, a current Mac or current WinRAR and WinZip. No sample had a .DS_Store file, so we can't describe one.

How do you strip metadata from a ZIP archive?

Build it clean, because fixing a finished one mostly didn't work. We tried five things and re-read the bytes after each.

MethodBeforeAfter
zip -rX when you create itUTC times, last-opened times and user IDs on all 5 entriesAll gone, 260 bytes smaller. Names, local times, permissions and the Unix byte stay
zip -X old.zip --out new.zip on a finished archiveThe same extrasNo change. Same size, same fields
Copy to a clean folder, chmod 644, touch one date, then TZ=UTC zip -X -D from inside itHome path, real dates, 0600 permissionsBare file names, one identical date, 0644, no folder entries
zip -z with empty inputAn archive comment and a per-file commentArchive comment gone. The per-file comment stayed
7z a -tzip -mtm=offHigh-precision time fieldField gone, and the date reads 1980-01-01 00:00:00

The third row is the one to copy. Row two is the trap: -X only applies to files being added. On the Mac sample, zip -d file.zip "__MACOSX/*" removed both extras, but the real file kept its user ID and times.

Does cleaning the ZIP clean the files inside?

No. Files came out byte for byte identical from every archive we made, cleaned ones included. Our test photo still had its GPS position and artist name. The .docx still said who wrote it.

So clean the contents first. None of our tools cleans a ZIP's own records, and our Document Metadata Remover turned away a .zip when we tried one. It takes .docx, .xlsx, .pptx and .pdf. Frequently Asked Questions

Do ZIP files have metadata?

Yes. Every entry has a name with its folder path, a modified time, a size and a checksum. Some tools add UTC and last-opened times, a numeric user ID, permissions and comments.

Does a password-protected ZIP hide file names?

No. In our test, unzip listed every file name, size and date without the password. A 7-Zip .7z archive made with -mhe=on did hide its file list.

Does zipping a photo remove its EXIF data?

No. The photo we pulled out of every test archive was identical to the original, GPS position included. Strip the photo first, then zip it.

How do I remove metadata from a ZIP file?

Rebuild it. Copy the files to a clean folder, set one date on all of them, and run zip with -X from inside that folder. Running -X on a finished archive changed nothing in our test.

What is the __MACOSX folder in a ZIP?

It's where a Mac puts each file's extra attributes. In the sample we read, it held a hidden file with an access list and account names. Deleting it left the real file intact.
